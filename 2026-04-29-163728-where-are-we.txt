❯ Can you explain me where the weird 0.9999 number comes from?                  

  Read 1 file (ctrl+o to expand)

⏺ It comes from inverse-variance fusion — a statistics technique for combining
  two noisy estimates of the same thing.

  ---
  The problem

  You have two ways to estimate filter clogging (ΔP/ΔP₀):
  1. Vibration proxy — invert the IMU signal model
  2. CT proxy — invert the current clamp signal model

  Both are noisy. How much should you trust each one? The minimum-variance
  answer: weight each proxy by the inverse of its variance. The noisier proxy
  gets less weight.

  ---
  The math

  W_VIB = σ_ct² / (σ_vib² + σ_ct²)

  You need σ for each proxy. Both are propagated from the Signal Inventory noise
   specs through the inversion formulas:

  σ_vib — the IMU averages 1660 samples per second (1660 Hz). Noise averages
  down by √N:
  σ_rms_ac ≈ 0.002 g / √(2 × 1660) ≈ 3.47e-5 g
  σ_vib    ≈ 3.47e-5 / (A_FUND_CLEAN × harmonic_factor) ≈ 9.2e-4

  σ_ct — the CT clamp gives 1 sample per second. No averaging benefit:
  σ_ct = 0.05 A / (I0 × BETA)
       = 0.05 / (4.0 × 0.12) ≈ 0.1042   (heating regime)
       = 0.05 / (9.0 × 0.12) ≈ 0.0463   (cooling regime)

  Plugging in:
  W_VIB_heating = 0.1042² / (9.2e-4² + 0.1042²) ≈ 0.99992
  W_VIB_cooling = 0.0463² / (9.2e-4² + 0.0463²) ≈ 0.99961

  The two regimes differ by only 3.1×10⁻⁴ — smaller than the noise floor. So one
   scalar was used: W_VIB = 0.9999 (the mid-point, four significant figures).

  ---
  The intuition

  The IMU samples at 1660 Hz and averages all of them. The CT clamp gives one
  number per second. That 1660× averaging advantage crushes the CT's noise
  contribution — the vibration proxy is ~100× more precise, so it gets 99.99% of
   the weight.

  The CT is still in the formula (at 0.01% weight) rather than zero, because
  dropping it entirely would be an architectural decision to retire the CT proxy
   from ΔP fusion — that would need its own Bill.

❯ is it flawed because you have more samples of IMU than CT?                    

⏺ Not flawed — it's an honest reflection of the current sensor architecture. But
   you're touching something real.

  The CT could sample faster. A 60 Hz AC power line completes 60 full cycles per
   second. If you sampled the current waveform at that rate and averaged 60
  samples per second instead of 1, σ_ct would drop by √60 ≈ 7.7×. That would
  shift W_VIB from ~0.9999 toward something more balanced, giving CT a
  meaningful voice in the ΔP estimate.

  The Case 5 ruling explicitly acknowledges this — it flags a future
  "decision-window-length Bill": at a 60-second decision window (N_ct = 60),
  CT's noise drops by √60 and the weights rebalance. Same logic applies if you
  increase the CT sampling rate within the current 1-second window.

  So the correct framing is:

  - W_VIB = 0.9999 is correct for the current design — 1 CT sample/sec is what
  the Signal Inventory specifies, and the math follows from that honestly.
  - The result is sensitive to that architecture choice. The IMU "wins" not
  because vibration is inherently a better proxy for filter clogging, but
  because you gave it 1660× more averaging budget.
  - It's a finding, not a flaw. It tells you the CT proxy is nearly useless for
  ΔP fusion as currently sampled. Whether to fix that (faster CT sampling,
  longer window) or retire CT from ΔP fusion entirely is a future Bill decision.

  The physics derivation is sound. What it's revealing is a design question
  worth revisiting once you have Stage 2 field data.

  The IMU is already running at 1.66 kHz — no extra cost there.

  The question is what it costs to increase the CT sampling rate. The nRF52840

  That ADC draws ~3.5 mA while active, with ~2 µs per conversion.

  ┌────────────────────────────────┬────────────┬─────────────────┐
  │            CT rate             │ Duty cycle │ Avg ADC current │
  ├────────────────────────────────┼────────────┼─────────────────┤
  │ 1 Hz (current)                 │ 0.0002%    │ ~7 nA           │
  ├────────────────────────────────┼────────────┼─────────────────┤
  │ 120 Hz (Nyquist for 60 Hz AC)  │ 0.024%     │ ~840 nA         │
  ├────────────────────────────────┼────────────┼─────────────────┤
  │ 600 Hz (practical RMS quality) │ 0.12%      │ ~4.2 µA         │
  ├────────────────────────────────┼────────────┼─────────────────┤
  │ 1.66 kHz (match IMU)           │ 0.33%      │ ~11.6 µA        │
  └────────────────────────────────┴────────────┴─────────────────┘

  For context the nRF52840 in active mode draws ~4.8 mA and the IMU draws ~0.9
  mA. Adding ~12 µA for 1.66 kHz CT sampling is a rounding error — less than
  0.2% of system power.

  The short answer: energy is not the reason to hesitate here.

  Two more useful things to note:
  1. You don't need 1.66 kHz for CT. A 60 Hz AC signal only needs 120 Hz
  Nyquist; 600 Hz gives good RMS quality. That already gets you √600 ≈ 24× noise
   reduction vs 1 sample/sec.
  2. The actual constraint is likely the signal conditioning circuit (burden
  resistor, filtering cap on the CT clamp output) — whether it can faithfully
  pass signal at those rates. That's a hardware question that needs the BOM
  filled in first.

❯ 600 Hz seems to be a good compromise. Otherwise, is there a way to make the   
  rms analogly for free?                                                        

⏺ Yes — this is a classic analog trick. It's called a true RMS-to-DC converter.

  How it works

  You put a small chip between the CT clamp output and the ADC. The chip
  continuously computes RMS in analog hardware (a squarer, low-pass filter, and
  square-root circuit) and outputs a DC voltage proportional to the RMS value.
  The nRF52840 ADC then just samples that DC output at 1 Hz — no waveform
  reconstruction, no CPU math.

  Common chips: LTC1966, AD8436, AD736. The LTC1966 is popular for this exact
  use case — low power, ~170 µA, handles signals down to below 60 Hz.

  Is it actually "free"?

  Not quite, but close:

  ┌──────────────────┬────────┬──────────────────┬───────────────┬─────────┐
  │     Approach     │  ADC   │     CPU cost     │    Extra      │  Power  │
  │                  │  rate  │                  │   component   │         │
  ├──────────────────┼────────┼──────────────────┼───────────────┼─────────┤
  │ Current (raw, 1  │ 1 Hz   │ none             │ none          │ ~0      │
  │ Hz)              │        │                  │               │         │
  ├──────────────────┼────────┼──────────────────┼───────────────┼─────────┤
  │ 600 Hz           │ 600 Hz │ RMS calc in      │ none          │ ~4 µA   │
  │ oversampling     │        │ firmware         │               │ ADC     │
  ├──────────────────┼────────┼──────────────────┼───────────────┼─────────┤
  │ Analog RMS-to-DC │ 1–10   │ none             │ RMS chip      │ ~170 µA │
  │                  │ Hz     │                  │               │         │
  └──────────────────┴────────┴──────────────────┴───────────────┴─────────┘

  The analog chip actually costs more power than 600 Hz oversampling (~170 µA vs
   ~4 µA). The "free" part is CPU cycles and firmware complexity — you skip the
  RMS computation entirely.

  One important caveat

  An analog RMS chip only makes sense if your motor current is reasonably 
  sinusoidal. HVAC blower motors driven by variable-frequency drives (VFDs) or
  soft starters produce non-sinusoidal current — the waveform has significant
  harmonics. A true-RMS chip handles that fine; a simple peak-detector approach
  (diode + capacitor) does not.

  Since this is a retrofit kit on unknown hardware, a true-RMS chip is the safer
   analog choice over a peak detector.

  Bottom line

  600 Hz oversampling in firmware is simpler (no extra BOM component, negligible
   power) and gives you the waveform data if you ever want it for other
  analysis. The analog RMS chip saves firmware complexity but costs more power
  and adds a component — which at this stage would be a BOM Bill. Worth
  revisiting once you have a target hardware configuration locked.
